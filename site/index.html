What does a robot model really learn? One test at a time.

A record of my project with one SO-101 arm and a small parcel sorting setup. The arm learns from my own demonstrations: pick a parcel from a heap, put it in a flip zone, turn the label down, push it out. I trained Diffusion Policy and SmolVLA, then tested, broke and fixed them, step by step, to make them more reliable.

How I test a model

Robot time is slow and a robot run is one sample. So each model goes through the same checks, from the setup to the robot benchmark.

🔧

Fix the setup first

A hard model problem is often an easy setup fix: a camera one joint back, a new base height, a pick and place in place of a push.

🎥

Clean, consistent demos

The same home pose, a heap schedule, phase marks. I check the start states and drop bad episodes before I train.

🚦

A guard on each training run

The loss is logged at each checkpoint. An offline check at a middle checkpoint (5k or 10k steps) has pass rules: the arm leaves home, the old skill stays, the new one improves. A run that fails stops there.

📊

Offline tests before the robot

On held-out demos: action error against the human, the flip decision, an image swap (does it look?), a start test (does it leave home?) and a language test (does it read the text?).

🏷

Robot runs scored by a script

Each parcel label has a marker, so software counts the result. I also check every video for hands: a run with help is not a run with no help.

⚖

One change at a time

Each round changes one thing, the data or the recipe, and has a control run. Then a difference has one cause.

Lesson: the offline ranking is not the robot ranking. SmolVLA had the best offline fit, but Diffusion-BSP was the best on the robot. Offline tests filter models; the robot decides.

Model 1 · Diffusion Policy + B-spline

Diffusion-BSP: the reliable one

Diffusion Policy (89M parameters) trained from scratch on the 99 pick-and-place demos. With B-spline execution, each plan is a smooth curve, and a 50 Hz control loop follows it at a set speed.

Smooth

Each new plan started 7-9° away from the last one, so the arm jerked. 5 denoising steps and a 0.2 s blend between plans cut direction reversals from 4.6 to 0.5 per second.

Speed you can set

The motion speed is one setting. At 1.5× it takes 15-23 s per parcel; my own demos took about 25 s. Faster fails more often.

Fast plans

A TensorRT FP16 engine cut the plan time from 88 ms to 18 ms on the robot, with the output within 0.15° of the original.

Reach

Its failure: parcels at the far edge

The arm can reach, but only 14 of 99 demos grasp that far, so the model stops short. Fix options: a smaller tray inside the strong reach, or more demos there.

Model 2 · SmolVLA

SmolVLA: a vision-language-action model, first try

SmolVLA (450M parameters) starts from a model that already knows images and text. I trained its action part (100M) on the same 99 demos for 80k steps, 27 hours on the laptop.

Best offline fit

The lowest action error on the demos (1.91° against 2.02° for Diffusion) and correct flip decisions.

Slow on the robot

It waited at home for 17-27 s and hovered for up to 75 s before a grasp. Every flip it did was correct: the problem is the grasp decision, not the motion.

Faster plans, same result

Half precision and a compiled denoising step cut a plan from 325 ms to 141 ms. Success did not change: the failures come from the model, not from speed.

Lesson: few demos of a state give no skill for that state. The fix is more demos of the failed states, not more training steps.

Model 3 · SmolVLA, trained with care

SmolVLA with proper training and data preparation

The same model, but each new piece of data is tested before it reaches the robot.

a

Corrections of all failures: the arm stayed at home

I took over with the leader arm when the model failed, and added 83 corrections. The new model did not leave home. A start test found the cause: corrections start in the middle of the task, and they pulled the model away from the start motion (wrist turn 32° → 3.7°).

b

One skill at a time, with a gate

Short far-edge fragments kept the start, and the far-edge grasp worked on the robot. 20 box-on-box demos, shown 3 times in training, cut the box error from 3.5° to 1.4°. The start test picks the checkpoint before any robot run.

c

Skill texts: does the model read the text?

Texts that differ in one word ("box" or "bag") had no effect (0.4°, below the 1.6° noise). Texts with no shared word work: the bag text fits 89 % of the bag frames (chance: 20 %). With 5 skills, the first three stayed as good, but a new skill needs about 20 demos: 13-16 were too few.

d

A person as the planner

On the robot, a key sends a skill text during the run. The top-box text lifts only the top box; the bag text then takes the bag. The image picks the target, the text picks the skill.

Lesson: split the job. A planner decides what to do, and the learned arm does how. The arm part works. The weak part is the view: the planner and the arm both take two touching dark parcels as one.

Setup fixes that beat model fixes

The hardware should get the same attention as the model. Each of these took less time than more training.

ProblemSetup fix
The 180° label flip made the wrist camera hit the tableCamera one joint back. Full flip, no contact.
Grasps were hard at the old angle New base height. An easier grasp angle on every parcel.
Pushing parcels out of the heap was slow and different each timePick and place, not push. One 2 s move to the flip zone for every parcel.
Results depended on who counted Markers on labels. A script scores each run.

First make the model reliable for the task. Then make it faster. Speed work before that wastes time and focus.

Where it stands

Done and measured

  • Pick, place, flip and push for bags and boxes, learned from demos
  • Heaps of up to 4 parcels cleared with no help, but not often (1 of 6 runs at 4 parcels)
  • Smooth motion at a set speed, 5× faster plans on the robot
  • New skills from demos: far edge, box on a box
  • A text picks the skill on the robot (a person as the planner)

Open

  • Black box against black bag, most of all when they touch
  • Parcels that fall onto the table: no demo shows the recovery
  • An automatic planner that separates touching parcels
  • Heaps as large as the demos (5 parcels) with no help, and a higher success rate at 4
  • Long runs on many heaps, for a success rate with error bars

Next steps

A planner that sees

The arm already follows the skill text. Next: a parcel detector that separates touching parcels, so the planner can pick the text on its own.

More demos per skill

About 20 or more for each new skill, and the same scene with two texts if the text must also pick the target.

Long runs

Many heaps and long runs, to give a success rate with error bars.

Each denoise step is ~1,200 small kernels. The CPU launches them slower than the GPU runs them: launch-bound, not compute-bound. torch.compile fuses them; step 13.2 → 3.4 ms.

A Parcel Sorting Cell with a Low-Cost Robot Arm

A robot cell that takes parcels from a heap, turns each one label down and pushes it to the next station. I built it as an engineer who wants to deploy it, not as a researcher: every choice in the hardware, the data and the AI model is measured against cycle time, reliability, damage to parcels and equipment, and cost.

What a deployable cell needs I wrote these first. Every finding below is tagged with the requirements it affects.

Reliable

Clears a full heap with no operator help. Every help call is labour cost.

Cycle time

Seconds per parcel sets the throughput of the line.

Gentle

No scratched or dropped parcels, no hits on the table, conveyor or other parcels.

Simple

Few parts and one model where possible. Easy to set up and to fix on site.

Efficient

Runs on low-cost compute; trains in hours on one small GPU.

Maintainable

A new parcel type or case can be added without breaking the old ones.

Cell design comes first Hardware and automation planning removed problems that no model could fix.

DecisionWhy Effect on the cell
Wrist camera one joint back
GentleReliable 		The label flip needs a 180° wrist roll. The camera mount turned with the roll and hit the table. Full flip with no table contact. The camera still sees the gripper.
Robot base height
ReliableCycle time 		I changed the height of the base against the tray, so the gripper meets the parcels at an easier angle. Easier grasps for the operator and the model.
Grasp, not push
Cycle timeGentle 		Pushing parcels out of the heap was slow (25-35 s per pull) and different every time. A side-wall grasp, the same as the flip, carries the parcel in 2-2.5 s. One repeatable motion for all parcel kinds, less sliding of parcels on the surface.
Stay in the strong part of the reach
Reliable 		At the far edge of the tray, the model found the parcel but did not reach the last few cm. Only 14 of 99 demos grasp that far. Size the infeed to the reliable reach, or pay for extra demos there.
Top camera at 848×480
Reliable 		At 1280×720 the encoder dropped frames. 848×480 has the same field of view with less than half the pixels. Clean training data and no lost frames at run time.
ArUco shipping labels
Maintainable 		Each parcel has a label with a unique marker, so a script can score label-down results. A repeatable benchmark that does not depend on a person.

Speed as a setting

Normal models send short action chunks, so their speed is tied to the inference rate. B-spline execution (BSP) turns each prediction into a smooth curve that a 50 Hz loop follows by clock time. Speed is then one setting.

  • BSP models flip a bag in 14-18 s; the demos take about 25 s.
  • The first runs jerked at each new curve. A 0.2 s blend cut direction reversals from 4.6 to 0.5 per second: less wear on the servos and fewer shaken parcels.

Servo lagThe arm lags its command by 13-30°, also at 1×Higher speed means harder contact when it goes wrong

Adding a new case without breaking the old ones Maintainable A new parcel type or heap shape will come. What does it cost to add it?

The model failed on a box on a box and on parcels at the far edge. I added 20 box-stack demos and 16 far-edge corrections (fb), then 30 more corrections on stacks (fbs, DAgger).

  • fb learned both cases and kept the old skill.
  • fbs took stacks well (3/5, all middle stacks good), but used the stack grasp on normal boxes and sorted only 2/5 of a normal heap.
Part of the fbs training mixShare of frames
Original demos (old skill)58 %
Box-stack demos (repeated 3×)33 %
Far-edge corrections5 %
Stack corrections4 %

The new case had too much weight, and it got that weight twice (fbs started from fb). A box on a box looks almost like a box next to a box, and all data had the same task text, so the model could not tell which skill to use.

Impact: each correction round costs operator time and can break a skill that worked. Record one good demo set for the new case, fine-tune once on a balanced mix, and check the old cases before release.

Next: a skill planner

A small vision-language model looks at the cameras at home and answers yes/no questions (box on a box? parcel at the far edge?). Code applies a fixed priority and tells the policy which skill to run, as in Hi Robot and π0.5. Offline, on 120 labelled frames, it picked the right skill 81 % of the time and found 23 of 25 stacks. The open risk is 12 false "stack" calls, the same failure as fbs.

Lessons for deployment

  • Fix the cell before the model. A camera that hits the table or a parcel out of reach is a hardware problem.
  • Know the robot's limits. Reach, servo lag and planning time set the safe speed and the tray size.
  • Pick models on the robot. The offline best model was not the best on the robot.
  • Speed is a trade-off. 1.5× cuts cycle time; 2× fails more and hits harder.
  • Count side effects, not only success. Pushed, dropped and stacked parcels cost more than a slow cycle.
  • Add skills once, balanced. Chained correction rounds cost operator time and break old skills.
